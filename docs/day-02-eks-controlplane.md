# Day 2 — EKS 컨트롤플레인

> 목표: Day 1의 VPC 위에 **쿠버네티스의 두뇌**를 올린다.
> 아직 파드를 돌릴 컴퓨트는 없다. 명령을 받을 API 서버만 먼저 세운다.

## 컨트롤플레인이 뭔가

쿠버네티스는 크게 두 부분입니다.

```
   컨트롤플레인 (두뇌)              워커 노드 (근육)
   ┌──────────────────┐            ┌──────────────┐
   │ API 서버         │            │   kubelet    │
   │ 스케줄러         │  ←────→    │   파드들     │
   │ 컨트롤러 매니저  │            │              │
   │ etcd (상태 저장) │            └──────────────┘
   └──────────────────┘              ↑ Day 3에서 만듦
     ↑ 오늘 만드는 것
```

**EKS의 핵심은 "컨트롤플레인을 AWS가 대신 운영해준다"는 것**입니다.
직접 쿠버네티스를 설치하면 etcd 백업, API 서버 이중화, 버전 업그레이드를 전부
직접 해야 합니다. EKS는 그걸 AWS가 하고, 우리는 시간당 $0.10을 냅니다.

그래서 오늘 만드는 건 **EC2 인스턴스가 아닙니다.** AWS 계정 어딘가에서 돌아가는
관리형 서비스이고, 우리에게는 **접속 주소(엔드포인트)** 만 주어집니다.

## 오늘 만드는 것 — 3개

```
┌─ IAM 역할 ────────────────────────┐
│ deepagent-eks-lab-cluster-role    │  ① EKS가 내 계정에서 일할 권한
│   └ AmazonEKSClusterPolicy 부착   │  ②   그 역할에 붙는 권한 정책
└───────────────────────────────────┘
                 ↓ 이 역할을 쓰며
┌─ EKS 클러스터 ────────────────────┐
│ deepagent-eks-lab-cluster (v1.36) │  ③ 컨트롤플레인 본체
│   프라이빗 서브넷 2개에 ENI 생성   │
└───────────────────────────────────┘
```

## 핵심 개념

### 1. IAM 역할 — 신뢰 정책 vs 권한 정책

가장 헷갈리는 부분입니다. **역할 하나에 두 종류의 정책이 붙습니다.**

| 구분 | 질문 | 코드 | 값 |
|------|------|------|-----|
| **신뢰 정책** | *누가* 이 역할을 빌릴 수 있나 | `assume_role_policy` | `eks.amazonaws.com` |
| **권한 정책** | 빌린 뒤 *무엇을* 할 수 있나 | `aws_iam_role_policy_attachment` | `AmazonEKSClusterPolicy` |

비유하면 신뢰 정책은 **출입증을 발급받을 자격**, 권한 정책은 **그 출입증으로 열 수 있는 문**입니다.
둘 중 하나만 있으면 동작하지 않습니다.

### 2. EKS는 왜 내 계정 권한이 필요한가

컨트롤플레인은 AWS가 운영하지만, **내 VPC 안에서 실제 작업을 합니다**:
- 프라이빗 서브넷에 ENI(네트워크 카드)를 만들어 워커 노드와 통신
- Service type LoadBalancer를 만들면 실제 ELB를 생성
- 노드 상태를 감시

이건 전부 내 계정의 리소스를 건드리는 일이므로 허가가 필요합니다.

### 3. ENI vs 엔드포인트 — 두 개의 다른 통로

`subnet_ids`에 적은 서브넷에 EKS가 ENI를 만듭니다. 그런데 이건 **API 서버 주소와 다릅니다.**

| | 무엇 | 어디에 | 누가 씀 |
|---|------|--------|---------|
| **ENI** | 컨트롤플레인이 내 VPC에 뻗은 손 | 내 프라이빗 서브넷 | 컨트롤플레인 → 노드 (kubectl exec/logs 등) |
| **엔드포인트** | 쿠버네티스 API 서버 주소 | AWS 관리 영역 | 나 / 노드 → 컨트롤플레인 |

엔드포인트는 두 종류를 켤 수 있습니다.

- `endpoint_private_access` — VPC 안에서 접근. 워커 노드가 씁니다.
- `endpoint_public_access` — 인터넷에서 접근. **내 맥북의 kubectl이 씁니다.**

**학습용이라 둘 다 켰습니다.** public을 끄면 VPC 안에 bastion 호스트를 띄워야
kubectl을 쓸 수 있어서, 비용과 번거로움이 늘어납니다.

> 퍼블릭 엔드포인트가 열려 있다고 아무나 들어오는 건 아닙니다.
> **IAM 인증을 통과해야** API 서버가 응답합니다. 그래도 조이고 싶으면
> `cluster_public_access_cidrs`를 `["<내 공인IP>/32"]`로 바꾸면 됩니다.
> (집/카페를 오가면 IP가 바뀌어 매번 고쳐야 하니 학습 중엔 권하지 않습니다)

### 3-1. 서브넷 vs ENI — 헷갈리기 쉬운 층위

"ENI가 프라이빗 서브넷에 있다"는 표현이 두 개념을 섞은 것처럼 들리지만,
섞인 게 아니라 **층이 다릅니다.**

| | 무엇 | 물리 비유 |
|---|------|-----------|
| **서브넷** | IP 대역 + AZ + 라우팅을 묶은 **네트워크 구간** | 사무실 한 층에 깔린 **랜선망(스위치)** |
| **ENI** | IP를 받아 그 망에 붙는 **가상 랜카드** | 그 스위치에 **꽂힌 랜카드** |

서브넷은 IP를 **나눠주는 쪽**, ENI는 **받아 가는 쪽**입니다.
실제로 우리 클러스터의 ENI IP는 예외 없이 해당 서브넷 대역 안에 들어 있습니다.

| ENI IP | 속한 서브넷 CIDR | AZ |
|--------|------------------|-----|
| `10.0.39.10` | `10.0.32.0/20` (private-2a) | 2a |
| `10.0.48.169` | `10.0.48.0/20` (private-2c) | 2c |
| `10.0.9.187` | `10.0.0.0/20` (public-2a) — Day 1의 NAT | 2a |

#### 핵심: AWS에서 서브넷에 "들어가는" 것은 ENI뿐입니다

```
❌ "EC2 인스턴스가 서브넷 안에 있다"
✅ "EC2의 ENI가 서브넷 안에 있고, 인스턴스가 그 ENI를 붙들고 있다"

❌ "EKS 컨트롤플레인이 내 프라이빗 서브넷에 있다"
✅ "컨트롤플레인의 ENI만 내 프라이빗 서브넷에 있다"  ← 본체는 AWS 계정에
```

**VPC 안의 모든 IP는 반드시 어떤 ENI에 속합니다.** EC2, NAT, VPC 엔드포인트,
RDS, Lambda(VPC 연결 시), 그리고 EKS 컨트롤플레인까지 전부 ENI를 통해서만
내 네트워크에 발을 들입니다. 내 EC2가 0개인데도 내 서브넷에 IP가 잡혀 있는
이유가 이것입니다 — **몸통은 AWS 계정에, 손(ENI)만 내 서브넷에.**

여기서 따라오는 규칙 두 가지:

1. **ENI는 서브넷 하나에 영구 귀속됩니다.** 나중에 옮길 수 없고, 따라서 AZ도 고정입니다.
   EKS가 AZ 2개를 요구하는 건 "ENI를 AZ마다 하나씩 두기 위해"입니다.
2. **보안그룹은 인스턴스가 아니라 ENI에 붙습니다.** 콘솔이 인스턴스 화면에서 보여줘서
   오해하기 쉽습니다. EKS가 자동 생성한 클러스터 보안그룹도 정확히는
   **컨트롤플레인 ENI에 붙은** 것입니다.

이 개념은 Day 3(노드의 ENI)과 Day 6(파드가 VPC IP를 받는 VPC CNI의 원리)에서 계속 돌아옵니다.

### 4. authentication_mode = "API"

IAM 사용자를 쿠버네티스 권한에 연결하는 방식이 두 가지입니다.

- `CONFIG_MAP` — 옛 방식. 클러스터 안의 `aws-auth` ConfigMap을 직접 편집.
  실수로 망가뜨리면 **아무도 클러스터에 못 들어가는** 사고가 유명합니다.
- `API` — 현재 방식(EKS Access Entries). AWS API로 관리해서 안전하고 되돌리기 쉽습니다.

새로 만들 때는 `API`를 씁니다. Day 4에서 자세히 다룹니다.

`bootstrap_cluster_creator_admin_permissions = true`는 **클러스터를 만든 IAM 주체
(지금은 `deepagent` 사용자)에게 자동으로 관리자 권한**을 줍니다.
이게 없으면 클러스터를 만들어 놓고도 `kubectl`이 거부당합니다.

## 실습 순서

```bash
make plan     # "Plan: 3 to add" 확인 — Day 1의 14개는 건드리지 않음
make apply    # ⏱️ 10분 안팎 걸립니다. 커피 한 잔.
```

생성 후 확인:

```bash
terraform -chdir=terraform output

# 클러스터 상태를 AWS에 직접 물어보기
aws eks describe-cluster --name deepagent-eks-lab-cluster \
  --query "cluster.{Status:status,Version:version,Endpoint:endpoint}" --output table

# EKS가 프라이빗 서브넷에 만든 ENI 확인 (개념 3번의 실물)
aws ec2 describe-network-interfaces \
  --filters "Name=description,Values=*deepagent-eks-lab-cluster*" \
  --query "NetworkInterfaces[].{Subnet:SubnetId,IP:PrivateIpAddress,Desc:Description}" --output table
```
